## 一、产品概述

### 1.1 产品定位

COSMIC-GUI 是一款 **COSMIC 功能点度量自动化工具**，帮助项目管理人员快速、高效地完成 COSMIC 全流程编写工作。

### 1.2 核心价值

| 痛点 | 解决方案 |
|------|----------|
| COSMIC 编写耗时（动辄 3000+ 行） | 自动化填充 + AI 辅助生成 |
| 人工填写容易遗漏、重复 | 规则引擎 + 去重机制 |
| 从截图到功能清单全靠人工 | AI 多模态识图自动提取 |
| Excel 转 Word 排版繁琐 | 一键转换 + 自动生成流程图 |
| 建表语句与 COSMIC 数据属性脱节 | DDL 解析 + AI 关联填充 |

### 1.3 当前版本状态（v1.0 已实现）

- Page1 欢迎页
- Page2 自动填充（规则引擎填写 H/J/L 列）
- Page3 LLM 填充（调用大模型填写 M 列）
- Page4 Excel 转 Word

## 二、功能需求

### 模块一：COSMIC 人天单价计算器（编写前）

**优先级**：P1  
**新增/优化**：新增

#### 2.1.1 需求描述

在编写 COSMIC 之前，帮助用户快速计算本次项目需要编写的功能点行数。

#### 2.1.2 输入参数

| 参数 | 类型 | 说明 | 示例 |
|------|------|------|------|
| 项目金额 | 数值（元） | 项目合同总金额 | 500000 |
| 预计扣减率 | 百分比（%） | 预计的成本扣减比例 | 15 |
| 人天单价 | 数值（元/天） | 每人天的单价 | 1500 |

#### 2.1.3 计算公式

```
工作量（行数） = 项目金额 / (1 - 预计扣减率%) / 人天单价
```

> 注：1 行 COSMIC = 1 人天工作量

#### 2.1.4 输出

- 计算结果：需要编写的 COSMIC 行数（向上取整）
- 附加信息：实际预算金额（扣除扣减后）

#### 2.1.5 UI 设计要求

- 简洁的表单页面，三个输入框 + 一个计算按钮
- 结果区域醒目展示计算行数
- 提供「复制结果」按钮，方便用户粘贴到项目计划中

### 模块二：AI 识图生成功能清单（编写前）

**优先级**：P1  
**新增/优化**：新增

#### 2.2.1 需求描述

用户将软件页面截图放入指定文件夹，提供系统名称和系统描述作为上下文，工具调用多模态大模型识别截图中的功能结构，自动生成一份带层级缩进的「功能清单」TXT 文件。此清单为 AI 初稿，**必须经人工审核、修改、补充后**才能用于后续流程。

> **核心原则**：AI 是辅助手段，人工审核才是唯一可靠来源。AI 的作用是帮人类出一版大概的内容，减少从零开始的工作量。

#### 2.2.2 用户输入

页面表单包含以下字段：

| 输入项 | 类型 | 必填 | 说明 | 示例 |
|--------|------|------|------|------|
| 系统名称 | 文本 | 是 | 即一级功能名称，整个系统的名称 | 客户端用户感知分析能力 |
| 系统描述 | 文本 | 是 | 一句话说清楚系统是什么 | 面向运营商的客户端用户体验质量分析平台 |
| 截图文件夹路径 | 文件夹选择 | 是 | 包含 JPG/PNG 截图的文件夹 | D:\screenshots\ |
| API Key | 文本 | 是 | 多模态模型的 API 密钥 | sk-xxx |
| API URL | 文本 | 是 | 模型接口地址 | https://api.openai.com/v1 |
| 模型名称 | 文本 | 是 | 使用的模型标识 | gpt-4o / qwen-vl-max |

#### 2.2.3 截图支持

- 遍历文件夹中所有 JPG/PNG 文件
- 支持两种截图粒度：
  - **整页截图**：一张图包含整个页面，AI 识别其中所有功能点
  - **功能拆分截图**：每张图对应一个功能模块
- 按文件名排序依次识别

#### 2.2.4 处理流程

```
用户填写：系统名称 + 系统描述 + 截图文件夹 + API 配置
    ↓
遍历文件夹中所有图片（JPG/PNG），按文件名排序
    ↓
逐张/批量调用多模态模型（系统名称+描述作为上下文，图片作为输入）
    ↓
AI 返回带层级缩进的功能结构文本
    ↓
合并所有图片的识别结果，输出为 TXT 文件
    ↓
用户在界面中人工复核、编辑、补充
    ↓
确认后保存为「功能清单 TXT」→ 供模块三使用
```

#### 2.2.5 AI 输出格式（TXT）

AI 输出为纯文本，使用**序号 + 缩进**表示层级关系，**不使用**树形符号（├── 等）。

**格式规范：**

```
1 二级功能名称
  1.1 三级功能名称
        查询XXX数据
        查询YYY信息
        导出ZZZ报表
  1.2 三级功能名称
        查询AAA状态
        查询BBB详情
2 二级功能名称
  2.1 三级功能名称
        添加CCC记录
        修改DDD配置
```

**层级说明：**

| 层级 | 缩进 | 序号格式 | 对应 Excel 列 |
|------|------|----------|--------------|
| 一级功能 | 无 | 无序号（由用户输入的系统名称决定） | C 列 |
| 二级功能 | 无缩进 | `1`、`2`、`3`... | D 列 |
| 三级功能 | 2空格 | `1.1`、`1.2`、`2.1`... | E 列 |
| 功能过程 | 8空格 | 无序号，每行一个功能 | I 列 |

**约束：**
- 输出中文
- 功能名称简洁明确，使用「查询/添加/修改/删除/导出/展示」等动词开头
- 不输出 F（功能用户）和 G（功能用户需求）列的内容

#### 2.2.6 提示词设计要点

```
系统上下文：
- 系统名称：{system_name}
- 系统描述：{system_desc}

指令：
1. 仔细观察截图中的软件界面
2. 识别页面中的功能模块和具体功能点
3. 按照以下层级结构输出：
   - 二级功能（功能大类，如"手机APP监控"）
   - 三级功能（大类下的细分，如"启动分析"）
   - 功能过程（具体可执行的操作，如"查询APP启动次数"）
4. 每个三级功能下列出尽可能完整的功能过程
5. 功能过程用动词开头，如：查询XXX、添加XXX、修改XXX、删除XXX、导出XXX

输出格式要求：
- 使用序号+缩进，不使用树形符号
- 二级功能：无缩进，序号为 1、2、3...
- 三级功能：2空格缩进，序号为 1.1、1.2...
- 功能过程：8空格缩进，无序号
```

#### 2.2.7 输出

- **TXT 文件**：带层级缩进的功能清单文本
- 输出路径：用户指定（默认与截图文件夹同目录）

#### 2.2.8 人工复核

- TXT 文件在外部编辑器中修改（如记事本、VS Code）
- 工具提供「打开文件」按钮，调用系统默认文本编辑器
- 用户修改完成后，点击「确认完成」进入模块三

#### 2.2.9 UI 设计要求

- 页面分为上下两部分：
  - **上方**：输入表单（系统名称、系统描述、截图文件夹、API 配置）
  - **下方**：操作区（开始识别按钮 + 进度条 + 日志输出）
- 识别完成后：
  - 显示「打开功能清单」按钮（用系统默认编辑器打开 TXT）
  - 显示「确认完成，生成 Excel」按钮（跳转到模块三）

### 模块三：功能清单生成 COSMIC Excel（编写前）

**优先级**：P1  
**新增/优化**：新增

#### 2.3.1 需求描述

将模块二产出的、经人工审核确认的「功能清单 TXT」，按照 COSMIC 模板格式生成 Excel 文件。生成的 Excel 包含完整的层级结构、合并单元格、以及 ERWX 数据移动类型，可被已实现的自动填充（模块四）和 LLM 填充（模块五）直接使用。

#### 2.3.2 输入

| 输入项 | 说明 | 来源 |
|--------|------|------|
| 功能清单 TXT | 经人工审核的层级文本 | 模块二产出 |
| 系统名称 | 一级功能 / 需求名称 | 用户在模块二输入 |

#### 2.3.3 输出

- Excel 文件，格式与 `cosmic-自动填充-模板-轻量级.xlsx` 一致
- 包含：正确的列结构、合并单元格、ERWX 数据移动类型

#### 2.3.4 模板列结构（14列）

| 列号 | 列名 | 模块三是否生成 | 生成规则 |
|------|------|---------------|----------|
| A | 修订标识 | 否 | 留空 |
| B | 需求名称 | 是 | = 用户输入的系统名称，合并所有行 |
| C | 一级功能 | 是 | = 用户输入的系统名称，合并所有行 |
| D | 二级功能 | 是 | 从 TXT 解析，同名合并单元格 |
| E | 三级功能 | 是 | 从 TXT 解析，同名合并单元格 |
| F | 功能用户 | 否 | 留空（后续人工填写） |
| G | 功能用户需求 | 否 | 留空（后续人工填写） |
| H | 触发事件 | 否 | 留空，但需按 I 列合并单元格对齐 |
| I | 功能过程 | 是 | 从 TXT 解析，每个功能过程合并 4 行（ERWX） |
| J | 子过程描述 | 否 | 留空（由模块四自动填充） |
| K | 数据移动类型 | 是 | 每个 I 填充 4 行：E / R / W / X |
| L | 数据组 | 否 | 留空（由模块四自动填充） |
| M | 数据属性 | 否 | 留空（由模块五 LLM 填充） |
| N | CFP | 否 | 留空 |

#### 2.3.5 TXT 解析规则

**输入 TXT 格式（示例）：**

```
1 手机APP监控
    1.1 启动分析
        查询APP启动次数
        查询APP流畅启动占比
        查询APP慢启动占比
    1.2 应用崩溃
        查询APP崩溃次数
        查询APP崩溃影响用户数
2 网络质量监控
    2.1 网络延迟
        查询网络延迟数据
```

**解析逻辑：**

| 步骤 | 说明 |
|------|------|
| 1 | 逐行读取 TXT |
| 2 | 识别层级：无缩进+数字序号 → 二级功能(D)；4空格+数字序号 → 三级功能(E)；8空格+无序号 → 功能过程(I) |
| 3 | 记录当前层级上下文（当前二级、当前三级） |
| 4 | 为每个功能过程(I) 生成 4 行数据（E/R/W/X） |

#### 2.3.6 合并单元格规则

| 列 | 合并规则 | 示例 |
|----|----------|------|
| B（需求名称） | 整列合并为一个单元格 | B2:B{n} |
| C（一级功能） | 整列合并为一个单元格 | C2:C{n} |
| D（二级功能） | 同一二级功能下的所有行合并 | D2:D20（"手机APP监控"） |
| E（三级功能） | 同一三级功能下的所有行合并 | E2:E12（"启动分析"） |
| F（功能用户） | 整列合并为一个单元格（留空） | F2:F{n} |
| H（触发事件） | 按 I 列的合并范围对齐 | 每 4 行合并一次 |
| I（功能过程） | 每个功能过程合并 4 行 | I2:I5（"查询APP启动次数"） |

#### 2.3.7 数据移动类型（K 列）规则

**每个功能过程(I) 对应 4 行，K 列依次为：**

| 行序 | K 列值 | 含义 | 关键词特征 |
|------|--------|------|-----------|
| 1 | E | 输入（Entry） | 功能过程名含「查询」「搜索」「获取」「输入」「导入」等 |
| 2 | R | 读取（Read） | 表示从存储读取数据 |
| 3 | W | 写入（Write） | 功能过程名含「保存」「添加」「修改」「删除」「写入」等 |
| 4 | X | 输出/展示（eXit） | 表示数据输出或界面展示 |

**生成示例（以"查询APP启动次数"为例）：**

| I 列 | K 列 |
|-------|------|
| 查询APP启动次数 | E |
| 查询APP启动次数 | R |
| 查询APP启动次数 | W |
| 查询APP启动次数 | X |

> 注：模板中旧数据只有 E/R/X 三行，新版统一改为 E/R/W/X 四行。

#### 2.3.8 完整生成示例

**输入 TXT：**

```
1 手机APP监控
  1.1 启动分析
        查询APP启动次数
        查询APP流畅启动占比
```

**输出 Excel（关键列）：**

| 行 | B | C | D | E | F | H | I | K |
|----|---|---|---|---|---|---|---|---|
| 2 | 客户端用户感知分析能力 | 客户端用户感知分析能力 | 手机APP监控 | 启动分析 | (空) | (空) | 查询APP启动次数 | E |
| 3 | ↑合并 | ↑合并 | ↑合并 | ↑合并 | ↑合并 | (空) | ↑合并 | R |
| 4 | ↑合并 | ↑合并 | ↑合并 | ↑合并 | ↑合并 | (空) | ↑合并 | W |
| 5 | ↑合并 | ↑合并 | ↑合并 | ↑合并 | ↑合并 | (空) | ↑合并 | X |
| 6 | ↑合并 | ↑合并 | ↑合并 | ↑合并 | ↑合并 | (空) | 查询APP流畅启动占比 | E |
| 7 | ↑合并 | ↑合并 | ↑合并 | ↑合并 | ↑合并 | (空) | ↑合并 | R |
| 8 | ↑合并 | ↑合并 | ↑合并 | ↑合并 | ↑合并 | (空) | ↑合并 | W |
| 9 | ↑合并 | ↑合并 | ↑合并 | ↑合并 | ↑合并 | (空) | ↑合并 | X |

#### 2.3.9 UI 设计要求

- 输入：TXT 文件选择 + 系统名称输入
- 预览区域：以表格形式展示生成的 Excel 内容（可滚动查看）
- 合并单元格在预览中以视觉方式呈现（灰色背景或跨行显示）

  - 「选择 TXT 文件」

### 模块五：建表语句辅助填充数据属性（编写中）

**优先级**：P1  
**新增/优化**：功能扩充

#### 2.5.1 需求描述

在原有 LLM 填充数据属性（M 列）的基础上，新增一个可选项：用户可以提供数据库建表语句（SQL DDL），工具解析其中的表结构和字段信息，作为 LLM 的上下文，使生成的数据属性更贴合实际系统。


#### 2.5.2 输入

| 输入项 | 说明 |
|--------|------|
| DDL 文件夹路径 | 用户将 `.sql` 文件放入指定文件夹 |
| Excel 文件 | 待填充的 COSMIC Excel |
| API 配置 | 复用 Page3 的 API Key / URL / 模型配置 |

#### 2.5.3 处理流程

```
用户选择 DDL 文件夹
    ↓
遍历文件夹中所有 .sql 文件
    ↓
解析 CREATE TABLE 语句 → 提取表名 + 字段列表
    ↓
调用 LLM 将字段翻译为中文（表名中文释义 + 字段中文释义）
    ↓
构建上下文：{表名(中文): [字段1(中文), 字段2(中文), ...]}
    ↓
填充 M 列时，将此上下文注入 Prompt
    ↓
LLM 依据真实表字段生成数据属性（适当扩充，避免大面积重复）
```

#### 2.5.4 DDL 解析规则

- 仅支持标准 SQL `CREATE TABLE` 语法
- 提取：表名、字段名、字段类型、注释（如有 COMMENT）
- 兼容 MySQL / PostgreSQL / Oracle 常见语法变体

#### 2.5.5 填充策略

| 要求 | 说明 |
|------|------|
| 依据真实字段 | 优先使用 DDL 中的实际字段名 |
| 适当扩充 | 字段数量有限时，可合理扩展相关字段 |
| 避免大面积重复 | 相邻行之间需有差异，不可整段复制 |
| 可选开启 | 用户可选择是否启用 DDL 辅助，不启用则走原有纯 LLM 模式 |

#### 2.5.6 UI 设计要求

- 在 Page3（LLM 填充页）新增一个可折叠区域：「建表语句辅助」
- 包含：文件夹选择按钮 + DDL 文件预览（显示解析出的表和字段数量）
- 一个开关 Checkbox：「启用建表语句辅助填充」
- 启用后，日志区域显示解析进度和翻译结果

### 模块七：自动画流程图（编写后）

**优先级**：P1  
**新增/优化**：新增

#### 2.7.1 需求描述

在 Excel 转 Word 的过程中，自动为每个四级标题或五级标题下方生成一张 Mermaid 时序图（sequenceDiagram），渲染为图片后插入 Word 文档。

#### 2.7.2 期望输出效果

```
1.1.1.2 业务功能流程图

[生成的时序图图片]

1、SRE运维人员向分层分级指标可视化管理平台发起前台业务办理时长采集任务巡检请求。
2、分层分级指标可视化管理平台调用数据库中的前台业务办理时长采集任务巡检接口。
3、...
```

#### 2.7.3 数据来源

从 Excel 中读取以下列，构建时序图数据：

| 列 | 用途 | Mermaid 角色 |
|----|------|-------------|
| F 列（发起方/接收方） | 解析出发起方和接收方 | participant |
| J 列（子过程描述） | 动作描述 | 箭头标注 |
| K 列（类型码） | 判断是否为返回动作 | 实线(->>) / 虚线(-->>) |

#### 2.7.4 Mermaid 生成逻辑

```python
# 核心逻辑（参考用户提供示例）
mermaid_code = "sequenceDiagram\n"
for each row:
    participant_a = 解析发起方(row[F列])
    participant_b = 解析接收方(row[F列])
    action = row[J列]
    arrow = "-->>" if 返回动作 else "->>"
    mermaid_code += f"{participant_a}{arrow}{participant_b}: {action}\n"
```

#### 2.7.5 渲染方案

```
Mermaid 代码 → mermaid-cli (mmdc) → PNG/SVG 图片 → python-docx 插入 Word
```

- 依赖：Node.js + @mermaid-js/mermaid-cli（mmdc 命令行工具）
- 备选方案：如未安装 mmdc，提示用户安装或提供离线渲染方案

#### 2.7.6 异常处理

| 场景 | 处理方式 |
|------|----------|
| F 列格式无法解析发起方/接收方 | 跳过该行，日志提示 |
| mmdc 未安装 | 提示安装命令，流程图部分跳过 |
| Mermaid 语法错误 | 记录错误，跳过该图，继续处理 |
| 标题下无数据行 | 不生成流程图 |

#### 2.7.7 UI 设计要求

- 在 Page4（Excel 转 Word 页）新增 Checkbox：「自动生成流程图」
- 勾选后显示 mmdc 安装状态检测（绿色/红色指示灯）
- 日志区域显示流程图生成进度（第 X/Y 张）

## 三、非功能性需求

### 3.1 架构设计要求

| 要求 | 说明 |
|------|------|
| 模块化 | 每个功能模块独立，可单独开发和测试 |
| 可扩展 | 新增功能只需添加新 Tab + 新页面，不改动已有代码 |
| Worker 模式 | 所有耗时操作（AI 调用、文件处理）必须在 QThread 中执行 |
| 统一配置 | API 配置（Key/URL/模型）全局共享，各页面复用 |

### 3.2 技术约束

| 约束 | 说明 |
|------|------|
| GUI 框架 | PyQt6（不变） |
| Word 处理 | python-docx |
| Excel 处理 | openpyxl |
| LLM 调用 | aiohttp（异步） |
| 流程图渲染 | mermaid-cli (mmdc)，需 Node.js 环境 |
| DDL 解析 | 自实现正则解析（不引入额外 SQL 解析库） |

### 3.3 兼容性

- Windows 10/11
- Python 3.10+
- 可选：Node.js（流程图功能依赖）

## 五、风险与依赖

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 多模态模型识别准确率不稳定 | 功能清单质量参差 | 人工复核环节 + 单张重识别 |
| mmdc 需要 Node.js 环境 | 增加用户安装成本 | 提供安装指引 + 无 Node.js 时降级为无图模式 |
| DDL 语法多样 | 解析失败 | 仅支持标准 SQL，异常时跳过并提示 |
| Tab 重构改动面大 | 可能引入回归 Bug | 保留原有页面代码，仅改容器和导航 |
